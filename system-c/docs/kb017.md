# KB017 — Expérience cnp_sha_check() : lookup SHA-1 exact vs matching sémantique

## Contexte

`cnp_check()` valide un terme de recherche (ex. un titre d'offre d'emploi réel) contre un CNP donné par matching sémantique approximatif : sous-chaînes à frontière de mot, singularisation naïve, expansion des variantes "/". Un audit adversarial exhaustif (kb015.md) a montré :
- 29 collisions résiduelles où deux professions différentes partagent un mot-racine
- Couverture large sur les variantes jamais indexées (titres d'employeurs)

Une hypothèse alternative a été explorée : remplacer ou compléter ce matching par une table de hachage SHA-1. Le principe : chaque appellation confirmée est hachée, regroupée par CNP, et le lookup se fait par identité exacte — O(1), sans aucun calcul sémantique.

**Propriété fondamentale testée** : SHA-1("infirmiere auxiliaire") et SHA-1("infirmieres auxiliaires") diffèrent totalement (effet avalanche). Un hachage ne peut donc pas produire de faux positif partiel — mais ne peut pas non plus reconnaître une variante jamais vue exactement.

Cette branche (`experimental/cnp-sha-check`) implémente `cnp_sha_check()` comme **fonction autonome**, sans dépendance vers `cnp_check()`, pour un test comparatif direct : même corpus, deux stratégies, comparer précision et couverture.

---

## Méthode de construction de la table (`build_sha_table.py`)

1. Charger `cnp-appellations-officielles.json` (516 CNP, source QualificationsQuébec)
2. Pour chaque CNP, pour chaque appellation (`appellation_principale` + `autres_appellations`) :
   - Normaliser : minuscules, accents retirés, espaces réduits (même `_normalize()` que `cnp_check.py`)
   - Expanser les variantes "/" en entrées séparées (même logique regex que `cnp_check.py`)
   - Calculer SHA-1 de chaque forme normalisée
   - Indexer : `{sha1_hex: cnp}`
3. **GARDE DE CONSTRUCTION** : si un même SHA-1 apparaît pour deux CNP différents → arrêt et rapport de collision

**Résultat** : 516 CNP, **2352 entrées SHA-1**, **0 collision détectée** — intégrité de la matrice source confirmée.

Structure du fichier généré (`cnp-sha-table.json`) :

```json
{
  "version": "1.0",
  "genere_depuis": "cnp-appellations-officielles.json",
  "nb_entrees": 2352,
  "blocs": {
    "<cnp>": {
      "appellation_principale": "...",
      "hashes": ["sha1_hex", ...]
    }
  },
  "index_inverse": {"sha1_hex": "<cnp>", ...}
}
```

## Analyse des résultats par catégorie

### Catégorie A — Round-trip (appellations officielles elles-mêmes)

Les deux algorithmes atteignent **100%**. C'est attendu : toutes les appellations officielles sont indexées dans la table SHA ET constituent des cibles naturelles pour le matching sémantique. Cette catégorie ne distingue pas les deux approches.

### Catégorie B — Autres appellations des 5 CNP cibles (390 variantes)

Les deux algorithmes atteignent **100%** (390/390). Toutes les `autres_appellations` sont indexées dans la table SHA — elles y sont entrées exactement lors de la construction. `cnp_check()` les retrouve aussi par matching exact ou partiel. Même résultat, vitesse très différente : SHA est **109×** plus rapide sur ce corpus (2.8 ms vs 305.3 ms).

### Catégorie C — Offres réelles jamais vues

C'est ici que les deux algorithmes divergent de façon caractéristique :

- **cnp_check()** : 28% (2/7). Retrouve "Infirmière auxiliaire" (via singularisation) et "Infirmier Infirmière" (via sous-chaîne). Manque les 5 autres — variantes avec parenthèses, "(temps partiel)", "(H/F)", constructions jamais vues.
- **cnp_sha_check()** : 0% (0/7). Aucune de ces 7 formes n'a été indexée exactement. C'est la propriété documentée du hachage — pas un bug.

**Note** : les 5 cas que cnp_check() rate aussi montrent que même le matching sémantique a ses limites face aux conventions d'écriture des employeurs (parenthèses, H/F, etc.).

### Catégorie D — Paires de collision connues (kb015.md)

- **cnp_check()** : 25/29 collisions reproduites (86%). Les 4 non-reproduites sont des paires où le terme déclencheur ne passe plus la garde de frontière de mot (résidu de Fix 3).
- **cnp_sha_check()** : **0/29 collisions reproduites**. Confirmé empiriquement — structurellement impossible par design. L'appellation principale de CNP A est un terme jamais vu tel quel pour CNP B → hash différent → aucun match.

**Confirmation de l'hypothèse** : le hachage ne peut pas produire de faux positif partiel. Zéro exception sur les 29 paires testées.

### Sweep exhaustif — 265 740 paires

| Métrique | cnp_check() | cnp_sha_check() |
|---|---|---|
| Faux positifs inter-CNP | 45 | **0** |
| Temps total | 317 760 ms (~5.3 min) | 2 435 ms (~2.4 s) |

Le nombre de FP de cnp_check() diffère légèrement de kb015 (45 vs 29) car ce sweep teste les appellations_principales contre tous les autres CNP, tandis que le sweep de kb015 incluait aussi les autres_appellations — deux méthodes de comptage légèrement différentes, résultat cohérent en ordre de grandeur.

## Conclusion — quand utiliser lequel

Les deux fonctions sont **complémentaires**, pas substituables. Aucune ne domine l'autre sur tous les cas.

| Critère | cnp_check() | cnp_sha_check() |
|---|---|---|
| Variantes jamais vues | **Oui** (partielle) | Non — aveugle |
| Faux positifs inter-CNP | ~45 sur 265 740 | **0** garanti |
| Vitesse | ~318 s pour 265 740 paires | **~2.4 s** (130×) |
| Confiance sur "valide=True" | Élevée mais non absolue | **Absolue** (identité exacte) |
| Confiance sur "valide=False" | Faible (peut rater) | Faible aussi (peut rater) |

**Architecture recommandée (kb015.md §"Évolution possible")** :

1. Essayer `cnp_sha_check()` en premier — O(1), 0 FP, résultat immédiat si connu
2. Si `sha_lookup()` retourne None → passer à `cnp_check()` pour les variantes inédites
3. Chaque nouvelle correspondance confirmée par revue humaine → ajouter à la table SHA via `build_sha_table.py` (rebuild complet) pour qu'elle soit disponible en O(1) la prochaine fois

Ce schéma exploite la complémentarité réelle des deux approches :
- SHA = mémoire exacte des cas déjà vus, ultra-rapide, précision absolue
- Sémantique = généralisation aux cas jamais vus, plus lente, précision moindre mais non nulle

**Sur ce corpus de test précis** : cnp_sha_check() domine pour la précision et la vitesse sur les données indexées ; cnp_check() est indispensable pour les variantes employeur jamais vues (corpus C : 2/7 vs 0/7).
